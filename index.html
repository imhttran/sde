When Adding AI Made Our Software Engineering System Less Reliable

What 61 failure scenarios taught us about deterministic decisions, AI agents, and the software development lifecycle.

We tested whether AI could improve software engineering decisions made by deterministic rules. In our experiments, the deterministic rules performed better. That result shaped an architecture decision: we kept explicit, testable rules in authority rather than promoting a more complex AI-assisted approach.

The interesting part was not the technology. It was the evidence. We had a hypothesis, a defined evaluation corpus, and measured results that gave us a reason to change our expectations.

The decision behind the workflow

When an AI agent encounters a failure during software development, the next action matters. Should it retry? Repair something? Stop? Ask a person to intervene?

These choices affect both progress and control. An unnecessary escalation interrupts work that could continue safely. A missed human-intervention boundary can let a workflow continue when it should pause. A system that always stops may appear cautious, but it can also become unusable.

We wanted to know whether AI could improve those choices by interpreting the evidence surrounding a failure. A deterministic engine provided the baseline. AI-assisted approaches were evaluated against the same set of 61 scenarios.

What we measured

The experiments took place in SOP, our SDLC harness for AI-assisted software development. SOP brings execution, verification, and human decision boundaries into a structured workflow. This made the decision layer a concrete engineering problem rather than an abstract debate about AI.

We compared recorded decisions with the corpus labels and examined safety and latency alongside accuracy. The headline results were:

Recorded agreement with labels across 61 scenarios
ApproachCorrect decisions
Deterministic SOP47/61 (77.0%)
SOP + CLEF/Nimble40/61 (65.6%)
JEV shadow evaluation8/61 (13.1%)

The deterministic baseline was imperfect. It still missed an escalation. But the AI approaches did not resolve that gap. Instead, they introduced unnecessary escalations or missed other human-intervention boundaries. Improving the prompt did not produce evidence that justified promoting the AI-assisted architecture.

Safety, escalation, and latency

The deterministic and CLEF/Nimble results were a paired evaluation across 61 scenarios, using exact agreement with frozen labels. The advisory path added the following outcomes and overhead:

MetricResult
Useful escalations0
False escalations19
Unsafe misses prevented0
Median added latency3.2 seconds
p95 added latency9.7 seconds
Nimble backup usage9 of 32 consultations

Why did the advisory path perform worse?

The most important finding was a mismatch between the question asked of the model and the decision made from its answer. The model was effectively asked, “How risky is this change: LOW, MEDIUM, or HIGH?” SOP then used a HIGH answer to require human intervention.

Those are different questions. A coding task can be high risk yet safely recoverable through deterministic tests, retries, and validation. Risk alone does not establish that the workflow must stop for a person.

A better advisory question would be: “Does this specific failure require human intervention, or can SOP safely continue under its existing governance controls?” This aligns the model’s assessment with the decision boundary being evaluated. Whether it improves the results still needs to be measured.

The proposed next experiment

Our recommendation is to disable advisory escalation by default for now while retaining the CLEF/Nimble integration and failover code. Then run a focused second evaluation using the corrected advisory question. Governance thresholds should stay unchanged until we know whether asking the right question improves classification quality.

What these results do—and do not—show

The corpus was relatively small, and its labels had not been independently adjudicated. The percentages describe agreement with those labels in this evaluation; they are not universal reliability scores.

JEV was also evaluated outside its primary code-review use case. Its shadow result should not be read as a head-to-head measure of model intelligence or as evidence that it lacks value for reviewing code. It tells us about this particular task and evaluation setup.

Those limitations matter. The conclusion is narrow: the approaches we tested did not demonstrate an improvement over our deterministic baseline for these decisions. That was sufficient to withhold promotion, while leaving room for a better-designed evaluation or a different use of AI.

The engineering lesson

AI can help interpret evidence without becoming the authority that decides what a system may do. That distinction gives us a useful design boundary: models can contribute analysis, while explicit policy governs execution and human approval.

This connects to deterministic verification and native development toolchains. A model can explain a change, but compilers and tests supply observable evidence. Likewise, a model can recommend a next step, while testable rules enforce the workflow’s boundaries.

We formed a hypothesis, tested it, and chose the simpler architecture because the additional complexity had not earned its place. The next step is to understand the baseline’s remaining gaps and evaluate improvements against stronger evidence.

The goal of AI-assisted software engineering isn’t to maximize the number of decisions made by AI. It’s to maximize the number of decisions we can trust.

AI & software quality

Why deterministic verification matters

AI can produce a convincing explanation of a code change. That explanation is useful context, but completion needs evidence from the software itself.

A compiler checks whether the program builds. A targeted test checks a specific behavior. Static analysis can reveal problems that a successful test run misses. Each tool answers a different question.

Deterministic verification makes those questions repeatable: a documented command, an identifiable source revision, and a result another engineer can inspect. The checks do not prove every possible behavior is correct. They establish exactly what was verified.

Match verification to the change. Small changes still deserve targeted checks; broader changes require broader evidence. Clear verification turns review into an assessment of observable results.

Development workflows

Keep the development toolchain native

An AI-assisted workflow should work with the same compiler, test runner, formatter, and build tools that developers already use.

Native tools provide a shared contract. A test failure remains a test failure whether a person or an agent made the change. Reviewers can reproduce the command and inspect its output without learning an extra interpretation layer.

The orchestration layer can choose tasks, collect results, and pause for human decisions. The development tools supply the evidence about the code.

This approach keeps the workflow understandable as it grows: explicit commands, clear exit conditions, and verification that stays close to the repository.
