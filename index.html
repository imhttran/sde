RAG · Rust migration · October 18, 2026

Migrating a RAG Service from Go to Rust with SOP: The Gotchas Were in the Workflow

Draft note: this account assumes the latest repair succeeded. Final parity, performance improvements, and fully autonomous completion are not claimed.

I wanted to see how far our agentic software engineering workflow could take a real migration.

The project was a RAG template written in Go. The target was Rust. SOP would organize the work, run implementation tasks, collect evidence, and control progression through the plan.

The useful question was whether that process could carry a working application across languages while preserving its behavior—and make unfinished work visible along the way.

We made progress. We also found cases where a task sounded complete before the software was complete. Those cases taught us more than a clean demo would have.

Moving behavior across languages

A RAG application has several connected responsibilities: ingest documents, create embeddings, store and retrieve relevant content, assemble a prompt, and generate an answer with citations.

A migration has to preserve those connections.

Compiling a Rust module proves something useful, but it does not prove that the query command calls it. A passing retrieval test does not prove that the answer service uses the retrieved passages correctly. A service test does not prove that the production binary can connect to PostgreSQL and communicate with the model endpoint.

We split the work into stages with explicit acceptance criteria. We also wanted to adopt existing Rust libraries where they fit. Building replacements for established infrastructure would have added work without helping us evaluate the migration.

SOP gave us a way to track those stages and their dependencies. The difficult part was deciding what evidence actually justified completing each stage.

The first gotcha: completion language was too easy to trust

Some implementation attempts reported completion without making the expected repository changes.

In other cases, the run stopped with NO_PROGRESS. The agent had read files and described its intentions, but the expected implementation was still missing.

That distinction matters. Discovery is useful when it resolves uncertainty. Repeated discovery without a write or a concrete blocker can consume an entire attempt.

Our response was to make the expected result more concrete: name the production component, identify the required behavior, and map each acceptance criterion to a check.

A completion statement became a claim to verify.

The second gotcha: tests needed to reach the production entry point

One repair exposed missing production pieces around the answer service and query command.

The expected AnswerService and query binary had not actually been written. We completed those pieces directly, then added acceptance tests around the service and the real query executable.

That produced two useful layers of evidence: five AnswerService tests checked service behavior, and four query-binary tests exercised the executable against PostgreSQL and a scripted Ollama server.

The scripted server made model responses predictable. PostgreSQL exercised the actual storage integration. Running the binary checked the wiring between those components.

This was stronger evidence than a set of isolated modules that happened to compile.

It also clarified the limits of the result. Controlled integration tests do not establish live model quality, complete ingestion support, or final parity with the Go application. Those requirements still needed their own checks.

The third gotcha: the runner needed Rust support too

The migration depended on more than the Rust code.

SOP also needed to recognize and permit the Cargo commands used by implementation and acceptance checks. We updated the configuration to use explicit cargo.agent_tool and cargo.acceptance_check settings.

That experience exposed a prerequisite we should have checked earlier: can the execution system perform the target language’s normal development workflow?

Before a migration starts, verify that the runner can inspect, edit, format, build, and test the target project under the intended permissions.

We also found an observability gap. One run recorded a denied tool call without preserving its name and arguments in the available sanitized trace. We could see that a denial occurred, but could not reconstruct the exact request.

That limited diagnosis. Useful failure evidence needs enough detail to explain what the agent attempted without exposing sensitive data.

The fourth gotcha: broad tasks encouraged broad exploration

The evaluation and parity stage was another trouble spot.

An attempt performed repository discovery but made no changes. We narrowed the task to the production eval command and separated the bilingual follow-up.

That gave the agent a smaller, reviewable outcome.

The important change was the task boundary. “Implement evaluation and parity” leaves room for extensive exploration. A task that identifies one command, its inputs, expected output, and acceptance checks gives the executor a clearer stopping point.

A task should be small enough that its result can be inspected independently.

Verification sometimes meant making no changes

One of the better outcomes came from a verify-first stage.

RUST-006C completed verification with zero agent calls. Existing work satisfied the mapped checks, so another implementation attempt was unnecessary.

This is a useful part of an agentic workflow: determine whether the required work already exists before asking an agent to recreate it.

We also kept known gaps explicit. Markdown/text ingestion and live end-to-end verification remained documented as unmet requirements during the narrower verification work.

Completing a stage should never make an unfinished requirement disappear.

Recovery was part of the engineering work

We did not finish every step through autonomous SOP execution.

Some tasks required direct implementation, narrower scope, or changes to the execution configuration. We recorded those interventions separately from SOP-executed work.

Retries also needed a reason. Updated tool support, corrected configuration, or a narrower task can justify another attempt. Repeating the same request after unchanged no-progress evidence is unlikely to help.

Approval boundaries still applied during recovery. An earlier authorization did not automatically authorize a new gate.

What I would carry into the next migration

I would keep the staged approach, but strengthen the starting contract.

Verify the target toolchain before implementation. Define concrete production outputs. Map acceptance criteria to executable checks. Test the real entry point early. Preserve diagnostic evidence. Reuse passing verification when its inputs have not changed.

Most of all, keep the report honest about who did the work and what was verified.

SOP helped organize the migration and expose missing evidence. The migration also exposed weaknesses in SOP’s task execution and reporting.

That made this useful dogfooding: the RAG application was the migration target, and the workflow itself was under test.

Adding Security Scanners to SOP: Making the Results Trustworthy

Published October 17, 2026. Updated October 19 with dependency-input coverage fixes, Cargo conformance testing, and the first production dependency baseline.

Adding a security scanner to a development workflow sounds straightforward. Run a command, read the output, and stop the build when it finds something serious.

That was the starting point for adding security scanning to SOP, our agentic software engineering workflow. We wanted an optional add-on that could use existing scanners and let people replace them with the tools they prefer.

The CLI integration was only part of the work. The harder questions appeared around it: What happens when the tool is missing? What does a clean result mean if half the targets were skipped? Can a resumed run trust an old report? Are exclusions actually preventing a scan, or just hiding findings afterward?

Those details determine whether a security gate is useful.

Start with existing tools and a small contract

We started with Semgrep Community Edition for source analysis and Gitleaks for secrets. We did not build a scanner engine or require a hosted AI service.

SOP handles orchestration, evidence, and policy. The scanners perform the analysis. Built-in adapters wrap their CLIs, and an external process adapter provides a versioned contract for other tools.

Replacement happens within a scan category. A different secret scanner can replace Gitleaks. It cannot satisfy a requirement for source analysis. A project can select several adapters when it needs several kinds of coverage.

The contract records findings, execution status, coverage, and provenance. It also keeps enough provider detail to explain where a finding came from. Normalizing reports should make them easier to use without stripping away their meaning.

Adding dependency scanning changed the selection problem

The next step was dependency coverage. We added OSV-Scanner alongside the source and secret scanners, with cargo-audit still available for Rust.

Different tools answer different security questions
ScannerRole in SOP
SemgrepSource analysis using configured Go and Rust rules
GitleaksSecrets detection across the declared repository scope
OSV-ScannerKnown dependency advisories for Go and Rust
cargo-auditAn alternative Rust dependency-advisory adapter

OSV does not replace Semgrep. An unsafe pattern in our code and a published advisory against a dependency are different kinds of evidence. A dependency-version match also does not establish that the vulnerable function is reachable. Our OSV adapter disables call analysis and records reachability as not evaluated.

Three categories do not impose a limit of three scanners. A project can use OSV for both Go and Rust, or select OSV for Go and cargo-audit for Rust. The second arrangement has two dependency adapters, each with a defined language scope.

That required more than choosing one tool per category. In a mixed repository, a successful Rust dependency audit cannot satisfy Go dependency coverage. SOP now selects adapters by capability and language, preserves explicit configuration, and reports overlapping selections. Automatic selection fills enabled, unconfigured coverage without silently replacing a configured scanner or running duplicate coverage.

The existing external adapter contract remains available. Once a compatible adapter is integrated, choosing it is a configuration change. Scanner-specific commands and parsing stay inside the adapter; policy and reporting stay in SOP.

Turning a scanner off must remain visible

We added controls at three levels: all security scanning, a category, or an individual adapter. This lets a project disable cargo-audit while keeping OSV, for example.

The precedence is explicit. Global disable wins over category and adapter settings. Category disable wins over an adapter's enable setting. Automatic selection cannot undo an explicit disable, and a failed scanner does not trigger an undeclared fallback.

A disabled scan is not a passed scan. Report-only mode records the gap. If an active required gate needs that coverage, disabling its scanner cannot satisfy the gate. Removing the requirement is a separate policy change.

Keep downloads separate from the scan

The OSV adapter uses a pinned executable and an explicit local advisory database cache. Provisioning downloads the tool and database archives; scan execution uses full offline mode. It does not refresh the database, send dependency information to the live API, or fall back to network scanning when local data is missing.

Go and Rust inputs are explicit: go.mod files and resolved Cargo.lock files, including nested modules and Cargo workspaces. The adapter uses a controlled empty scanner configuration so repository-local OSV ignores cannot silently suppress findings outside SOP policy.

Evidence includes input and database identities, freshness, scanner version, and configuration. A changed input or database invalidates reused evidence. Freshness is checked again during resume because an unchanged database can still become too old.

There is one deliberate setup requirement: OSV needs an explicit version pin and database path. Automatic selection does not invent that pin. Inspection reports an unpinned candidate as unsupported, explains the missing prerequisite, and keeps required-mode readiness blocked.

Review caught mistakes in our own summary

The scanner integrations were passing, but a later review found two defects in how SOP described coverage.

First, the category aggregation started with “covered” and did not handle “unconfigured.” In a mixed repository, covered Rust dependencies plus unconfigured Go dependencies could therefore produce a category summary of covered. The language details still showed the gap, but the headline contradicted them.

We changed aggregation to use explicit, order-independent states. Entirely unconfigured coverage stays unconfigured. Covered plus unconfigured becomes partial. A category is covered only when every applicable unit is covered.

Second, when every configured adapter was disabled, the runner returned before recording the disabled-adapter evidence. It reported that no adapter was configured, losing the distinction between an empty configuration and a deliberate choice to disable scanners.

The runner now retains those disabled records and their reasons before evaluating policy. Tests check the normalized result, CLI JSON, and human-readable output. An all-disabled scan remains indeterminate, and required coverage remains blocked.

Neither finding demonstrated a required-gate bypass. Both mattered because the report is what a person or another agent uses to decide what happened. Correct scanner output is not enough if the orchestration layer summarizes it incorrectly.

The implementation and follow-up fixes are merged in PR #65 and PR #69. The follow-up's final PR commit passed all 12 checks, including real Semgrep, Gitleaks, cargo-audit, and OSV integration. That establishes behavior under the tested conditions; it is not a new production baseline or proof of complete security coverage.

Count the inputs owed a scan

Further review found a deeper coverage problem: discovering existing lockfiles does not tell us whether every package has been accounted for. Two independent Rust packages with only one lockfile must not become a clean scan of the one file we found.

We added an inventory of dependency obligations. Each detected Go module and Rust package or workspace needs a supported input or an explicit explanation of what is missing. Selecting a subset keeps omitted obligations visible. Go source without a module cannot become a successful empty analysis, and a successful Rust scan cannot conceal an unsupported Go input.

The built-in OSV and cargo-audit adapters enforce that inventory. Its identity also participates in resume checks, so an earlier report cannot be reused after the expected inputs change. External adapters still depend on their contract; integrating one does not automatically establish the same inventory enforcement.

Check our assumptions against Cargo

Cargo workspace discovery needed a TOML parser and membership resolution rather than directory ancestry. We covered quoted declarations, workspace members, exclusions, path dependencies, and explicit workspace references. Absolute or repository-escaping workspace references are reported as unsupported layouts.

One proposed finding did not survive reproduction. We initially treated an ordinary file matched by a workspace member glob as an error. Pinned Cargo 1.98.0 ignores that file. We withdrew the finding and corrected the implementation. A matched directory without Cargo.toml still produces a diagnostic, including when valid members also match.

That correction matters: a security integration should not reject a valid repository because our model of the build tool was wrong. The regression tests now preserve both cases.

We also separated test time from production time. Cargo-audit fixtures use a controlled clock so their advisory snapshots do not unexpectedly age out as the calendar advances. Production still checks the actual time and retains the 90-day stale-data deny policy. Resume tests verify that aging data invalidates reusable evidence.

A scan has more than one result

We separated three questions:

QuestionExample result
Did the scanner execute?Completed, unavailable, timed out, failed
Did it cover the requested scope?Complete, partial, unknown
What does policy decide?Pass, fail, indeterminate

That separation matters. A missing binary is not a clean scan. A completed process with skipped source files does not establish complete coverage.

We also found an ordering issue during review: a blocking finding combined with partial coverage returned INDETERMINATE. We changed policy evaluation so a known blocking finding produces FAIL, while coverage remains PARTIAL. Incomplete coverage without a blocking finding still produces INDETERMINATE.

Report-only mode records those verdicts without blocking delivery. Required mode blocks on failures and insufficient evidence. The repository remains in report-only mode while its coverage and suppression policies are decided.

Real tools found problems the fixtures missed

Our first dogfood attempt could not complete the scans: Semgrep lacked configured local rules, and Gitleaks was unavailable. SOP correctly reported an indeterminate result, but that did not prove the adapters worked against real scanners.

We added pinned provisioning and real CLI integration tests with clean and seeded fixtures. Missing prerequisites fail the required integration job instead of quietly skipping it.

Those tests exposed practical differences in provider output. Semgrep could return a fingerprint placeholder that said requires login. Gitleaks could return absolute paths and fingerprints containing host-specific paths. Semgrep could also rewrite rule IDs using the local rules directory.

We added a stable fingerprint fallback, normalized paths, and disabled Semgrep rule-ID rewriting. A baseline should not change just because the rules moved to another directory.

Review also tightened the external adapter boundary. SOP validates the response protocol and uses its own observed content identity, configuration digest, and execution times rather than accepting those claims from the provider.

Exclusions need to mean the same thing everywhere

The baseline work exposed another problem: different adapters could interpret the same exclusion differently.

A broad sop-* pattern could exclude real packages under cmd/ when the intent was to exclude root-level binaries. Later review found that anchored patterns with multiple path components and wildcard subtree patterns were not handled consistently by our matcher.

We fixed the matcher and added real-scanner conformance tests over the same directory tree. The tests cover patterns such as /internal/*/testdata, **/generated/**, and /root-only.

Gitleaks needed a separate fix. Filtering excluded findings after parsing still allowed excluded files to consume scan time and fill the report. We changed the adapter to scan a filtered temporary view.

One regression test makes the distinction concrete: an excluded file contains 2,000 synthetic tokens, while the report limit is 1,024 bytes. The filtered scan completes with the included finding. The control scan without exclusions exceeds the limit.

Exclusions are part of the declared scope and appear in the evidence. Scanner-side skips remain coverage gaps. Unknown skip reasons conservatively produce partial coverage.

Evidence has to survive a retry

Each scan records the content identity, scanner version, rules identity, configuration, and policy. Resume reuses evidence only when the relevant identities match.

We also made the native reports usable from the resumed run. SOP verifies the prior sanitized report's digest and copies it into the current run. Missing or tampered evidence forces another scan.

Secret handling applies across that path. Detected values must stay out of normalized findings, diagnostics, saved reports, and model inputs. Tests check synthetic secret values, including short values that an earlier redaction implementation skipped.

Provisioning received the same attention. Semgrep and its dependencies now install from a hash-pinned lockfile. Production rules come from a pinned upstream commit with verified archive and file hashes. Rule content stays outside the repository rather than being redistributed with SOP.

Why required mode is still off

In that original baseline, Semgrep's default ignore policy skipped 578 Go test files, two test or fixture directories, and one minified file. Those numbers describe that run's rules and configuration. Enabling required mode still needs an explicit policy for the intended scan scope and reviewed findings; adding more adapters does not make that decision for us.

Required security failures now have their own classification and stop for operator review. They do not enter an automatic code-fix loop, and existing approval boundaries retain precedence.

That gives us a working add-on with replaceable scanners and verified evidence handling. Enabling a required gate is the next policy decision. It depends on agreeing what must be scanned and how reviewed findings will be managed.

This work reinforced a familiar engineering lesson: integrating a tool includes defining its failure behavior. For an agentic workflow, that behavior has to stay clear through retries, partial results, external adapters, and human decisions.

Adding scanners was straightforward compared with making their results trustworthy. The useful result is a report that tells us what ran, what it covered, what it found, and what remains unknown.

RAG · Engineering findings

We Built RAG Into Our AI Agent Workflow. Then We Decided Not to Use It.

What dogfooding SOP taught us about measuring value before adding complexity.

Explore the Agentic SOP source code on GitHub ↗

We wanted to know whether retrieval-augmented generation (RAG) could give our AI coding agents better context. So we integrated RAG into Agentic SOP, our AI-assisted development workflow. The technology worked, but after the evaluation we decided not to enable it by default.

We used SOP to build SOP

We dogfooded the project end to end. SOP helped us plan the integration, implement the retrieval client, manage PostgreSQL migration work, run tests, enforce human approval boundaries, and publish changes. The system being changed was also the process used to change it.

That exposed a validation problem: a Go test command could return success even when every integration test was skipped. We hardened SOP's PostgreSQL gate to require structured evidence of an executed passing test and verified the behavior through the real CLI pipeline.

What we built

Our RAG Template producer uses Go, PostgreSQL, pgvector, and Ollama embeddings. SOP retrieves authorized documents with citations, places them in bounded untrusted context, falls back when optional retrieval fails, and blocks a task if its required evidence is missing.

The related RAG Template Rust migration project is also available on GitHub. It is a separate project link; the retrieval results below describe the evaluated Go-based integration.

Fixing the evaluation

Our initial test used only two documents and identical synthetic zero-vector embeddings. That wasn't enough to evaluate semantic retrieval. We also found the ingestion command didn't assign corpus identity, leaving genuine embeddings inaccessible to corpus-scoped retrieval. We fixed this with an optional RAG_CORPUS setting.

The final evaluation used 12 sectioned documents with 12 distinct real 768-dimensional embeddings generated by nomic-embed-text and ten frozen queries. We compared PostgreSQL full-text ranking (ts_rank_cd) with hybrid RAG over the same document corpus.

Why we chose NO-GO

Our keyword baseline already found the expected documents, while hybrid retrieval did not demonstrate an improvement. Embeddings, ingestion, indexing, security, and operational overhead must earn their place. In this workload, we couldn't show that they did.

This is a deliberately narrow finding. The sample was small and its topic-matching queries favored keyword search. We didn't measure downstream coding quality or compare query latency between the two approaches. It does not mean RAG is generally ineffective.

What we did instead

We kept RAG opt-in and disabled by default, and built /sop-rag-integrate, a reusable skill that helps developers decide whether RAG belongs in their own application and choose suitable existing solutions. It can also recommend not adding RAG.

The goal wasn't to prove we could build RAG. It was to learn whether RAG made our system better. Keeping the simpler default was the engineering decision our evidence supported.

Decision systems · Experimental findings

When Adding AI Made Our Software Engineering System Less Reliable

What 61 failure scenarios taught us about deterministic decisions, AI agents, and the software development lifecycle.

We tested whether AI could improve software engineering decisions made by deterministic rules. In our experiments, the deterministic rules performed better. That result shaped an architecture decision: we kept explicit, testable rules in authority rather than promoting a more complex AI-assisted approach.

The interesting part was not the technology. It was the evidence. We had a hypothesis, a defined evaluation corpus, and measured results that gave us a reason to change our expectations.

The decision behind the workflow

When an AI agent encounters a failure during software development, the next action matters. Should it retry? Repair something? Stop? Ask a person to intervene?

These choices affect both progress and control. An unnecessary escalation interrupts work that could continue safely. A missed human-intervention boundary can let a workflow continue when it should pause. A system that always stops may appear cautious, but it can also become unusable.

We wanted to know whether AI could improve those choices by interpreting the evidence surrounding a failure. A deterministic engine provided the baseline. AI-assisted approaches were evaluated against the same set of 61 scenarios.

What we measured

The experiments took place in SOP, our SDLC harness for AI-assisted software development. SOP brings execution, verification, and human decision boundaries into a structured workflow. This made the decision layer a concrete engineering problem rather than an abstract debate about AI.

We compared recorded decisions with the corpus labels and examined safety and latency alongside accuracy. The headline results were:

Recorded agreement with labels across 61 scenarios
ApproachCorrect decisions
Deterministic SOP47/61 (77.0%)
SOP + CLEF/Nimble40/61 (65.6%)
JEV shadow evaluation8/61 (13.1%)

The deterministic baseline was imperfect. It still missed an escalation. But the AI approaches did not resolve that gap. Instead, they introduced unnecessary escalations or missed other human-intervention boundaries. Improving the prompt did not produce evidence that justified promoting the AI-assisted architecture.

Safety, escalation, and latency

The deterministic and CLEF/Nimble results were a paired evaluation across 61 scenarios, using exact agreement with frozen labels. The advisory path added the following outcomes and overhead:

Why did the advisory path perform worse?

The most important finding was a mismatch between the question asked of the model and the decision made from its answer. The model was effectively asked, “How risky is this change: LOW, MEDIUM, or HIGH?” SOP then used a HIGH answer to require human intervention.

Those are different questions. A coding task can be high risk yet safely recoverable through deterministic tests, retries, and validation. Risk alone does not establish that the workflow must stop for a person.

A better advisory question would be: “Does this specific failure require human intervention, or can SOP safely continue under its existing governance controls?” This aligns the model’s assessment with the decision boundary being evaluated. Whether it improves the results still needs to be measured.

The proposed next experiment

Our recommendation is to disable advisory escalation by default for now while retaining the CLEF/Nimble integration and failover code. Then run a focused second evaluation using the corrected advisory question. Governance thresholds should stay unchanged until we know whether asking the right question improves classification quality.

What these results do—and do not—show

The corpus was relatively small, and its labels had not been independently adjudicated. The percentages describe agreement with those labels in this evaluation; they are not universal reliability scores.

JEV was also evaluated outside its primary code-review use case. Its shadow result should not be read as a head-to-head measure of model intelligence or as evidence that it lacks value for reviewing code. It tells us about this particular task and evaluation setup.

Those limitations matter. The conclusion is narrow: the approaches we tested did not demonstrate an improvement over our deterministic baseline for these decisions. That was sufficient to withhold promotion, while leaving room for a better-designed evaluation or a different use of AI.

Follow-up: a disabled evaluator still controlled model routing

Update: October 17, 2026. A later routing smoke test exposed a dependency we had not removed. Explicitly selecting SMALL completed a local call to Ternary-Bonsai-2-27B-mlx-2bit. Explicitly selecting MEDIUM completed a cloud call to glm-5.3-flash:cloud. Both configured execution paths worked.

We then enabled automatic routing for two read-only test runs, without a model-class override. Both selected MEDIUM. Their recorded reason was JEV evidence unavailable; defaulting to medium.

The router required JEV evidence before a task could qualify for SMALL. Early JEV was disabled in the tested configuration, so the automatic path could not select SMALL—even when the available structural signals were within its small-task limits. Configuring a local model was not enough to make the workflow use it automatically.

This was a separate smoke test, not an extension of the 61-scenario evaluation. It established a routing dependency. The dependency remained unresolved at the time of this update. A possible next experiment is to determine whether verified task structure can qualify bounded work for SMALL without JEV, while unknown or higher-risk work remains on MEDIUM or LARGE. That policy needs its own tests; missing evidence must not silently become evidence of low risk.

The practical lesson extends beyond disabling an evaluator: inspect every downstream rule that still expects its output. A component can stop running while its absence continues to determine the system's behavior.

The engineering lesson

AI can help interpret evidence without becoming the authority that decides what a system may do. That distinction gives us a useful design boundary: models can contribute analysis, while explicit policy governs execution and human approval.

This connects to deterministic verification and native development toolchains. A model can explain a change, but compilers and tests supply observable evidence. Likewise, a model can recommend a next step, while testable rules enforce the workflow’s boundaries.

We formed a hypothesis, tested it, and chose the simpler architecture because the additional complexity had not earned its place. The next step is to understand the baseline’s remaining gaps and evaluate improvements against stronger evidence.

The goal of AI-assisted software engineering isn’t to maximize the number of decisions made by AI. It’s to maximize the number of decisions we can trust.

AI & software quality

Why Deterministic Verification Matters When AI Writes Code

AI has changed how quickly we can produce code. It can draft implementations, suggest fixes, and explain unfamiliar systems in seconds. But producing code quickly raises a familiar engineering question: how do we know the change is correct?

A convincing explanation is useful during review. It does not establish that the program compiles, preserves an API contract, or handles a failure correctly. As code generation becomes easier, the evidence used to accept that code becomes more important.

What deterministic verification means

Deterministic verification uses explicit checks with defined acceptance conditions. Given the same source, inputs, and controlled environment, those checks should produce repeatable results. A build succeeds or fails. A targeted test compares actual behavior with an expected outcome. Static analysis evaluates the code against known rules.

The environment matters. Dependency versions, configuration, clocks, randomness, and external services can all affect results. Repeatability requires controlling those inputs where practical and recording the conditions under which verification ran.

The goal is a result another engineer can reproduce and inspect, without depending on the original author’s confidence.

Separate generation from acceptance

An AI model can propose several plausible implementations of the same requirement. That flexibility is valuable when exploring a solution. Acceptance needs a stable contract: what behavior must hold, which checks demonstrate it, and what happens if a check fails.

Consider an agent changing retry logic. The code may look reasonable and the happy path may pass. Verification should also check that retries stop at the intended limit, permanent failures are handled correctly, and the operation does not duplicate work. Those expectations come from the system’s requirements.

The model can help write the tests. Engineers still need to review whether those tests capture the intended behavior, rather than simply confirming the implementation the model produced.

Use the tools closest to the code

Compilers, formatters, test runners, and static analysis tools already provide a shared engineering language. Using the repository’s native toolchain keeps verification understandable to developers and reproducible in CI.

Each check has a purpose. Compilation establishes that the code builds. Tests examine specified behavior. Static analysis can identify problems outside the exercised paths. A successful result from one tool should not be treated as a substitute for the others.

Match the evidence to the change

Verification should reflect scope and risk. A small behavior change may need a focused regression test and relevant checks. A change to authorization, concurrency, persistence, or a public interface deserves broader evidence, including affected integration paths.

Record the source revision, commands, and results. Make skipped checks visible. A repeatable process also needs a clear response to failure: repair the problem, narrow the claim, or request a human decision.

Deterministic verification does not prove that software is free of defects. Tests can miss cases, and requirements can be wrong. It makes the basis for acceptance explicit, exposes what remains unverified, and gives reviewers evidence they can challenge.

AI can accelerate implementation. Reliable delivery depends on making the criteria for accepting that implementation clear and testable.

Development workflows

Keep the development toolchain native

An AI-assisted workflow should work with the same compiler, test runner, formatter, and build tools that developers already use.

Native tools provide a shared contract. A test failure remains a test failure whether a person or an agent made the change. Reviewers can reproduce the command and inspect its output without learning an extra interpretation layer.

The orchestration layer can choose tasks, collect results, and pause for human decisions. The development tools supply the evidence about the code.

This approach keeps the workflow understandable as it grows: explicit commands, clear exit conditions, and verification that stays close to the repository.
